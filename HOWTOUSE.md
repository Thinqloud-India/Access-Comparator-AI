# How To Use

Everything needed to **configure and use** the Profile Access Manager component once it has already been deployed to an org (see `DEPLOYMENT.md` for install steps).

## 1. Add the Component to a Page

The component is exposed on three surfaces (`profileAccessManager.js-meta.xml`):

- `lightning__Tab` — a standalone Custom Tab
- `lightning__AppPage` — a Lightning App Page
- `lightning__HomePage` — the Home page

### Option A — Custom Tab (recommended for a dedicated admin tool)

1. Setup → **Tabs** → **Lightning Component Tabs** → **New**.
2. Lightning Component: **profileAccessManager**.
3. Tab Label: e.g. `Access Manager`. Tab Style: pick an icon (e.g. a shield or lock icon).
4. Save, then add the new tab to the appropriate **App** (e.g. a "Security Admin" Lightning App) via **App Manager → Edit → Navigation Items**.

### Option B — Lightning App Page

1. Setup → **Lightning App Builder** → **New** → **App Page** → One Region.
2. Drag **profileAccessManager** from the "Custom" component list onto the page.
3. Save and **Activate** — assign it to the desired Lightning App, and set org/profile visibility as needed.

## 2. Assign Access to the Right Users

This is a **security-configuration tool** — restrict who sees it.

1. Create (or reuse) a permission set / profile assignment, e.g. **"Access Auditor"**.
2. Grant that permission set access to the Tab/App Page created in Step 1 (Setup → Permission Sets → [name] → Assigned Apps / Object Settings / Tab Settings as applicable).
3. Assign the permission set only to Admins, Release Managers, or Security reviewers — see `PREREQUISITES.md` §4 for the underlying data-access permissions those users need.

No additional Custom Permission or Permission Set is shipped with the component — access control is entirely standard tab/page visibility plus the querying user's own Setup-read permissions.

## 3. Using Tab 1 — Profile Access

1. Open the component. The **Profile Access** tab loads automatically and lists all Profiles in the org.
2. Use the search box to filter by name, or **Select All** / **Deselect All**.
3. Check one or more profiles, then click **Get Profile Details (N)**.
4. Each selected profile appears as its own card with 8 sub-tabs: Object Permissions, Field Permissions, Apex Class Access, Visualforce Access, Tab Visibility, Application Access, Record Type Access, Custom Permissions.
5. Use **Expand All / Collapse All** and **Jump to** to navigate multiple profile cards; click **✕** on a card to dismiss it from view without re-querying.
6. Click **Generate Excel (N)** to download a multi-sheet `.xls` workbook of everything currently on screen. **Save this file** — it's the input the Access Comparison tab expects.
7. If you change your profile selection after results are shown, a banner warns the results are stale — click **Refresh Results** to re-query.

## 4. Using Tab 2 — Object Access

1. Switch to the **Object Access** tab.
2. Pick a category from the left nav: **Standard Objects**, **Custom Objects**, **Apex Classes**, **Apex Triggers**, **Visualforce Pages**, or **Flows & Processes**.
3. Search/filter (status, API version, process type filters appear where relevant), then select the items you want.
4. **For Standard/Custom Objects:** click **Analyze Object Security (N)** to get a full per-object security bundle (Object Permissions, Field-Level Security, Permission Sets, Permission Set Groups, Role Hierarchy, Record Types, Record-Level Access, and a **Security Limitations** tab that discloses what SOQL cannot retrieve — OWD, Sharing Rules, Tab Visibility).
5. **For Apex Classes / Visualforce Pages:** click **Analyze Access (N)** to see which Profiles/Permission Sets grant access to each selected item.
6. **For Apex Triggers / Flows & Processes:** no access-analysis step exists (triggers run regardless of grants; Flow access isn't exposed via SOQL) — just select and export.
7. Click **Generate Excel** to download the results. Save this file if you plan to use it in Access Comparison.

## 5. Using Tab 3 — Access Comparison

1. Switch to the **Access Comparison** tab.
2. Choose **Comparison Type**: `Profile Access` (compares `ProfileAccess_*.xls` exports) or `Object Access` (compares `ObjectSecurity_*.xls` exports). Switching type clears any uploaded files.
3. Upload the **UAT** file and the **Production** file — each must be a `.xls`/`.xlsx` export generated by this same component from Tab 1 or Tab 2 (per the Comparison Type selected). Invalid or mismatched files are rejected with a specific error.
4. Click **Compare Access** — the diff runs entirely in your browser (no data is sent anywhere). Summary cards show totals, matches, differences, and items missing on either side.
5. Use the **Status**, **Profile**, and **Object Search** filters, sortable column headers, and pagination (200/500/1000 rows per page) to explore results.
6. Click **Export Comparison Excel** to download a 3-sheet workbook (Comparison, Summary, Differences) covering **all** rows, not just the current filter/page.
7. *(Optional)* Click **✨ Analyze with Agentforce** for a plain-English narrative verdict and summary — requires the Agentforce setup described in `PREREQUISITES.md` §6. If unavailable, the button is replaced with an explanatory note and the deterministic comparison above still works fully.

## 6. Typical End-to-End Workflow (UAT vs. Production release check)

1. In the **UAT** org: go to Profile Access (or Object Access), select the profiles/objects in scope for the release, click Get Details / Analyze, then **Generate Excel**.
2. Repeat the identical selection in the **Production** org and **Generate Excel** there too.
3. In either org's **Access Comparison** tab, upload both files and click **Compare Access**.
4. Review the **Differences** and **Missing** rows — these are the access gaps to reconcile before or after go-live.
5. Export the comparison workbook and attach it to the release/change ticket as evidence.

## Notes & Limitations

- Field Permissions queries are capped at 50,000 rows per profile-detail call and object-security call is capped at 20,000 rows — very large orgs may need to select fewer profiles/objects per batch.
- Org-Wide Defaults, Sharing Rules, and Tab Visibility on the Object Access tab are **never fetched or estimated** — they always show as "Not Available Through SOQL" in the Security Limitations tab; verify these directly in Setup.
- Record-Level Access rows only appear where a generic `<Object>Share` table exists and is queryable; a note explains when it does not.
